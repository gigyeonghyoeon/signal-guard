## 1. 프로젝트 개요

### 1.1 프로젝트 명

**Signal Guard — 교통신호 상태정보 오류검지 시스템**

한국도로교통공단 제안요청서(2025.08)의 교통신호 상태정보 오류검지 과제를 수업용 웹 MVP로 줄인 것이다. 원사업은 18개 지자체 2,425개 교차로의 제공 신호가 실제 신호와 어긋나는 문제를 다룬다. 수업에서 검증하는 모집단은 인천시 727개소이고, 구현 대상은 그 안의 표본이다. 상태 값은 임의의 신호 데이터다.

한 줄로 말하면, **신호 계획(기대값)과 신호 상태(실측값)를 같은 교차로·시각·방향에서 대조해 오류를 찾고, 대시보드에서 보고, 제공 정보·계획·현장 요청으로 닫는 시스템**이다. 원본 수신은 덮어쓰지 않는다.

### 1.2 목표 및 범위

목표는 다음 다섯 가지다.

1. 교차로 마스터, 신호 계획, 신호 상태를 모아 저장한다. 상태 값은 임의의 신호 데이터다.
2. 누락, 정합성, 일관성, 계획 불일치, 수신 품질을 규칙으로 판정한다. 등급은 INFO, WARN, ERROR, CRITICAL이다.
3. 해결 가능한 오류는 제공 계층만 보정하고 이력을 남긴다. 해결 불가능한 오류는 이슈로 올린다.
4. 운영자와 관리자가 등급, 지연, 미처리 이슈를 한 화면에서 본다.
5. 오류를 정보 통제, 계획 통제, 현장 통제 요청으로 닫는다. 원본 수신은 그대로 둔다.

| 구분 | 이번 학기에 포함 | 범위 밖 |
|------|------------------|---------|
| 대상 | 인천 표본. 교차로 수는 설정으로 늘림 | 전국 2,425개소, 센터 내부망 |
| 상태 | 임의의 신호 데이터. 항목은 교차로, 8방향 잔여시간·점등상태 | 센터 전용회선 상시 연동 |
| 계획 | 공개 계획 데이터 수집·로컬 저장, 시드·수동 등록. UTIC는 승인 후 | UTIC 미승인을 결함으로 보지 않음 |
| 검지·관제 | 규칙 엔진, 자동보정, 이슈, 대시보드, 통계, 로그인·권한 | 기계학습 이상탐지 |
| 통제 | 제공 계층 수정, 계획 수정, 현장 통제 요청 기록 | 현장 신호제어기 실제어, 현장 출동 |
| 화면 | 대시보드, 교차로, 이슈, 계획, 통계, 설정. 갱신은 폴링 | 지도 관제, 웹소켓 |
| 기술 | React, Spring Boot, PostgreSQL. 로컬 실행 | 센터 반입, 보안 특약, 하자보수 계약 |

완료 기준은 유지한다. 필수 스토리 테스트 100%, 치명·주요 결함 0, 매뉴얼로 재설치와 시연이 가능해야 한다. 기능 동결은 11주 말이다.

팀 역할은 다음과 같다. 조찬희는 일정·요구·화면(대시보드, 이슈, 통계, 설정)과 발표를 맡는다. 기경현은 스키마, 수집, 규칙 엔진, API, 인증을 맡는다. 코드 리뷰와 통합, 문서는 함께 한다.

### 1.3 주요 변경 사항

1주차 착수안 이후 요구 ID는 지우지 않고, 입력과 처리 방식만 바꿨다.

| 일자 | 변경 | 이유 |
|------|------|------|
| 2026-09-18 | 비교 축을 계획 대 상태로 둠. 루프를 검지 → 관제 → 통제로 확장. 통제는 정보·계획·현장 요청. 원본은 불변 | 제안요청서가 비교 대상과 오류를 닫는 방법을 비워 둠 |
| 2026-10-10 | SFR-002를 부분 구현으로 둠. 대응 합계는 구현 6, 부분 구현 18, 문서·수업 대체 15 | 상태 검증은 임의의 신호 데이터로 한다 |
| 2026-10-11 | 스택을 React, Spring Boot, PostgreSQL로 확정 | 설계 게이트. 화면 구역과 API 경로·권한은 스택과 분리해 유지 |
| 2026-10-12 | 오류 처리를 수신 데이터 처리와 신호기 상태 처리로 나눔. 상황을 A–G로 분류 | 제공값만 고치면 화면은 바뀌어도 현장 점등은 그대로인 경우를 구분 |
| 2026-10-25 | 상태 값을 임의의 신호 데이터로 고정. 항목은 교차로 ID, 8방향 잔여시간·점등상태 | 같은 교차로를 계획과 반복해서 대조하기 위함 |

2026-10-12에 정한 처리 두 갈래는 이 보고서의 설계 결론이다.

| 갈래 | 고치는 대상 | 하는 일 |
|------|-------------|---------|
| 수신 데이터 처리 | 들어온 값과 운전자에게 나가는 제공값 | 단위·별칭·중복·결측을 제공 계층에서 고친다. 고칠 수 없으면 그 값을 내보내지 않는다. 원본은 유지한다 |
| 신호기 상태 처리 | 그 교차로 신호기의 점등·잔여·운영 모드·주기 시작 | 현시 복귀, 잔여 재동기, 운영 모드 복귀, 주기 재동기 중 하나를 낸다. 수업 시연의 신호기는 재생기다 |

상황 구분은 다음과 같다.

| 구분 | 예 | 닫는 처리 |
|------|----|-----------|
| A 수집·수신 | 타임아웃, 빈 응답, 중복 | 수신 데이터 처리 |
| B 값·형식 | 별칭, 결측, 단위가 섞임 | 수신 데이터 처리 |
| C 시계열 | 잔여시간 급증·급감, 같은 값 반복 | 반복이면 신호기 상태 처리 |
| D 현시 논리 | 황색 누락, 교차 방향 동시 녹색 | 신호기 상태 처리 |
| E 계획 대조 | 계획 불일치, 교차로 매핑 오류 | 원인을 가른 뒤 처리 |
| F 통제·운영 | 같은 보정 반복, 권한 없는 수정 | 수신 데이터 처리 |
| G 연쇄 | 여러 교차로가 같은 시각에 이상 | 상태가 확인될 때 신호기 상태 처리 |

명령을 만들지 않는 경우도 정해 두었다. 형식이 깨진 값, 수신이 비어 있음, 계획이 없음, 매핑이나 계획 자체의 오류, 긴급 우선·수동 운영 구간이다. 되돌릴 현시가 없거나, 그 시각의 계획으로 되돌리면 안 되는 경우다.

이 갈래는 요구사항 FR-CTL-004·CON-003(현장 요청은 기록만, 신호기 호출 0건)과 아직 한 문장으로 맞춰져 있지 않다. 7주차에는 재생기가 복귀 명령을 받아 다음 주기 점등을 바꾸는 쪽으로 시연을 잡았고, 요구 문서에 반영할지는 팀 결정으로 남아 있다. 4장 이슈로 둔다.

## 2. 계획 대비 진행 현황

일정 뼈대는 분석 1–3주, 설계 4–5주, 구현 6–11주, 테스트 12–13주, 안정화 14–15주다. 구현은 주 16 스토리 포인트, 필수 29건·96점이다. 9주차에 끝나 있어야 하는 마일스톤은 M4(검지 데모)다.

| 주 | 계획 | 9주차 현황 | 판정 |
|----|------|------------|------|
| 1–3 | 범위, 요구, 유스케이스, 백로그 고정 (M1) | 분석 산출물 완료 | 계획대로 |
| 4–5 | 아키텍처, 화면, ERD, API, 규칙, 프로토타입 (M2). 스택·표본 수·주기 확정 | 설계 산출물 완료. 스택은 10월 11일 확정. 표본 수와 수집 주기는 숫자로 고정하지 않음 | 산출물은 완료. 게이트 항목 일부는 열림 |
| 6 (S1) | 기동, 로그인, 역할별 셸 | 로그인·RBAC·감사 로그·앱 셸 완료. 운영자는 설정 메뉴가 막힘 | 계획대로 |
| 7 (S2) | 임의 신호 데이터 5개 교차로가 원본·정규화로 저장 (M3) | 임의의 신호 적재. 상황 ID A–G와 처리 두 갈래 문서. 계획 데이터 로컬 저장 | 적재는 계획대로 |
| 8 (S3) | 시드 계획이 붙은 교차로에서 엔진이 등급을 남김 | 검지 엔진이 등급을 남김. 계획 번호·주기·시간대를 수신과 함께 저장 | 계획대로 |
| 9 (S4) | 잔여 급변·중복·계획 불일치가 보정 또는 이슈로 갈림 (M4) | 대시보드가 저장된 신호로 오류·경고를 표시. 자동보정과 이슈 분기는 이후 | 엔진 판정은 되었고, 보정·이슈 분기는 미달 |
| 10–11 | 이슈 관제, 통제, 통계 후 기능 동결 (M5) | 해당 화면은 경로와 안내 문구만 있음 | 미착수 |
| 12–15 | 테스트, 매뉴얼, 시연 (M6, M7) | 착수 전 | 미착수 |

구현되어 동작하는 범위는 다음이다.

- **로그인.** 관리자·운영자 계정, 비밀번호 정책, JWT, 역할별 메뉴, 감사 로그. 로그인 API 테스트가 있다.
- **신호 계획 수집.** 공공데이터포털 교차로 계획 서비스에서 요일 계획, 운영 시간대, 예약을 읽어 로컬에 저장한다. 수신 행에 계획 번호, 주기, 시간대, 계획 수집 시각이 남는다. UTIC 수집은 승인 전이라 하지 않는다.
- **대시보드.** 저장된 신호로 대상 수, 건수, 오류, 경고를 보여 준다. 판정은 값 없음, 교차 방향 직진의 동시 녹색, 잔여시간이 계획 주기보다 큼까지다. 방향이 계획 현시와 맞는지는 판정하지 않는다. 이 판정의 단위 테스트가 있다.
- **저장.** 사용자·감사 로그 테이블과, 수집 회차·교차로 수신(원본 JSON 포함) 테이블이 마이그레이션으로 있다.

아직 코드로 닫히지 않은 범위는 다음이다.

- 자동보정 로그, 이슈 생성
- 재생기(복귀 명령을 받으면 다음 주기 점등을 바꿈)
- 교차로 상세, 이슈 처리, 계획 편집, 통제, 통계, 설정. 화면 자리는 라우팅되어 있고 본문은 이후 스프린트 안내만 있다

계획과 어긋난 방향은 두 가지다. 대시보드와 계획 저장은 10주 목표보다 앞에 있다. 임의 신호 적재와 검지 엔진은 6–8주 계획까지 되어 있다. 9주에 끝내기로 한 보정·이슈 분기는 뒤에 있다.

### 3.3 구현 (6–9주) — 진행 중

## 5. 향후 계획

11주 말 기능 동결과 15주 시연은 유지한다. 12주 전에 넣지 못한 검지는 테스트 주에 새로 만들지 않는다.

### 10주 — 밀린 검지를 시연 가능한 입력으로

1. 이슈 2를 결정한다. 재생기 명령을 요구사항에 반영하거나, 현장 쪽은 요청 기록만 남기기로 되돌린다.
2. 상태 값은 임의의 신호 데이터로 넣는다. 화면에는 입력 종류가 보인다.
3. 재생기를 준비한다. 복귀 명령을 받으면 다음 주기 점등을 바꾼다. 이 작업은 1번 결정이 명령 쪽일 때의 구현이다.
4. 규칙 중 R06, R03, R08, R10이 보정 또는 이슈로 갈라지게 한다. 원본 JSON은 그대로 둔다.
5. 시연 교차로 수와 넣는 간격을 숫자로 고정한다.

### 11주 — 시연 최소 세트 후 기능 동결

남기는 시연은 다음이다.

- 로그인 직후 오류 수, 자동보정 건수, 미처리 이슈가 보인다.
- 교차로 상세에서 원본과 제공 값이 나란히 보인다.
- 관리자는 제공 차단, 계획 수정, 현장 통제 요청을 남긴다. 운영자의 통제는 거부된다.
- 동시 녹색(S-D02)은 제공을 중지한다. 1번 결정이 명령 쪽이면 현시 복귀까지 보여 준다.

용량이 부족하면 다음 순서로 뺀다. 지도, 웹소켓, UTIC 자동 수집, 감시 제외, 계정 추가 화면, 통계 CSV, 교차로 ID 매핑 화면. 시연 계정 둘과 시드에 넣어 둔 매핑으로 대체한다.

11주 금요일에 기능을 동결한다. 그 이후 필수 기능은 추가하지 않는다.

### 12–13주 — 테스트

- 필수 스토리 테스트를 헤더(스프린트 / 스토리 / 요구 / 유스케이스)로 실행한다.
- 반드시 확인할 경우: 자동보정이 원본을 덮어쓰지 않음, 관리자 통제의 감사 로그, 운영자 통제 거부, 충돌 녹색의 등급.
- 대시보드·목록·상세·통계는 3초 안에 나오게 한다.
- 비밀번호 해시, 시크릿 미포함, 입력 검증을 점검한다.
- 통과 기준은 필수 스토리 100%, 치명·주요 결함 0이다.

### 14–15주 — 안정화와 시연

매뉴얼과 설치 가이드를 만들고, 다른 PC에서 재설치가 되는지 확인한 뒤 시연·발표를 한다. 시연 순서는 시뮬레이션 계획의 정상, 별칭·중복 보정, 잔여 급증, 동시 녹색, 계획 불일치, 수신 장애, 운영자 권한 거부 순이다.

### 9주차 이후 바로 보이는 완료 모습

10주 말에 같은 임의 데이터를 다시 넣으면 같은 등급이 나오고, 원본은 수집 당시 값 그대로다. 11주 말에 관리자 계정으로 그 오류를 정보·계획·현장 요청 중 하나로 닫을 수 있다.
