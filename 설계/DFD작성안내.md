# Signal Guard DFD 작성 안내

| 항목 | 내용 |
|------|------|
| 문서명 | DFD 작성 안내 |
| 프로젝트 | Signal Guard |
| 버전 | 1.0 |
| 작성일 | 2026-09-27 |
| 용도 | 자료흐름도를 직접 그릴 때 기호, 장 구성, 이 시스템에 넣을 이름을 고정한다 |
| 근거 | `분석/요구사항정의서.md` 2장·5장, `설계/시스템아키텍처.md` 3장·6장·7장·13장 |

이 문서는 그리는 방법과 도형에 적을 이름이다. 완성된 DFD 그림은 넣지 않는다.

---

## 1. 무엇을 그리는 그림인가

DFD는 화면 흐름이나 순서도가 아니다. **데이터가 시스템 밖에서 들어와, 어떤 처리를 거쳐, 어디에 쌓이고, 누구에게 나가는지**만 그린다.

| 그림 | 묻는 것 | 이 과제에서 |
|------|---------|-------------|
| 유스케이스 | 누가 어떤 목표를 이루나 | 이미 `유스케이스사용자스토리.md` |
| 화면 IA | 어느 화면으로 가나 | 이미 `설계/화면IA.md` |
| 순서도 | 조건에 따라 어느 단계로 가나 | DFD에 마름모를 넣지 않는다 |
| DFD | 데이터 이름과 방향 | 이 문서로 그린다 |

한 줄 정의는 요구사항 정의서와 같다. 계획(기대값)과 상태(실측값)를 수집·대조해 오류를 검지하고, 관제하고, 정보·계획·현장 요청으로 통제한다. **원본 수신은 수정하지 않는다.**

---

## 2. 기호

팀 안에서 한 가지만 쓴다. 아래는 Yourdon/DeMarco 기호다.

| 기호 | 이름 | 그리는 법 | 이름 붙이는 법 |
|------|------|-----------|----------------|
| 사각형 | 외부 개체 | 시스템 밖. 가장자리에 둔다 | 사람·기관·다른 시스템. 동사 금지 |
| 원 | 프로세스 | 데이터를 변환하는 일 | `번호 + 동사구`. 예: `3.0 오류 검지` |
| 평행선 두 줄 | 데이터 저장소 | 프로세스 사이에 남아 있는 데이터 | `D번호 + 명사`. 예: `D1 원본 수신` |
| 화살표 | 데이터 흐름 | 한 줄에 데이터 하나 | 명사. 예: `정규화 상태`. “조회한다”처럼 동사만 쓰지 않는다 |

규칙

- 화살표의 양 끝 중 **적어도 한쪽은 프로세스**다. 외부끼리, 저장소끼리는 잇지 않는다.
- 저장소에 들어가는 화살표는 쓰기, 나오는 화살표는 읽기다. 머리 방향을 바꾸면 의미가 바뀐다.
- 조건 분기는 마름모로 그리지 않는다. 프로세스에서 **이름이 다른 흐름이 둘 이상 나가게** 그린다. 예: `정상 상태`, `해결 불가 오류`.
- 한 장에 프로세스는 7개 안쪽으로 둔다. 넘치면 하위 장으로 내린다.

## 3. 그릴 장

세 장만 그리면 된다. 더 쪼개지 않는다.

| 장 | 프로세스 | 이 장에만 있는 것 |
|----|----------|-------------------|
| 배경도 | `0 신호 오류 검지` 하나 | 외부 개체와, 경계를 넘는 흐름 |
| 수준 0 | `1.0`~`7.0` | 시스템 안의 처리와 저장소 |
| 수준 1 | `1.0`, `3.0`, `4.0`, `5.0`만 분해 | 부모 장에 있던 입출력을 그대로 유지 |

`2.0 계획 관리`, `6.0 관제 조회`, `7.0 기준 설정`은 수준 0에서 멈춘다.

그리는 순서

1. 배경도의 외부 개체와 경계를 넘는 흐름 이름을 먼저 적는다.
2. 수준 0에서 그 흐름이 어느 프로세스로 들어가는지 정한다. 배경도에 없는 외부 화살표를 수준 0에 새로 만들지 않는다.
3. 저장소를 프로세스 아래에 두고, 원본이 제공 값과 다른 저장소인지 확인한다.
4. 수준 1은 부모 프로세스의 입출력을 표로 받아 적은 뒤에 원을 나눈다.

---

## 4. 배경도

가운데 원 하나에 `0 신호 오류 검지`라고 쓴다. 저장소는 그리지 않는다. 원 안이 시스템 안이다.

### 4.1 외부 개체

| 외부 개체 | 두는 이유 |
|-----------|-----------|
| 운영자 | 조회, 이슈 코멘트 |
| 관리자 | 통제, 계획 수정, 계정·수집·임계값 설정 |
| 녹화 픽스처 | 수업 기준 상태 입력. 실시간 API와 같은 종류의 데이터 |
| 실시간 신호 API | 공공데이터포털. 맵·잔여시간·점등상태. 호출은 보조 경로 |
| UTIC | 승인 후에만 TOD·SIGNALMAP·기반정보 |

운영자와 관리자를 한 상자로 합치지 않는다. 운영자에게서 통제 데이터가 나오면 요구사항과 어긋난다.

현장 신호제어기는 상자로 두지 않는다. 도표 밖에 한 줄만 적는다. “현장 신호제어기는 경계 밖이며 데이터 흐름이 없다.”

### 4.2 경계를 넘는 흐름

화살표마다 아래 이름만 쓴다.

| 출발 | 도착 | 데이터 |
|------|------|--------|
| 녹화 픽스처 | 0 | 녹화 상태 |
| 0 | 실시간 신호 API | 수집 요청 |
| 실시간 신호 API | 0 | 상태 응답 |
| 실시간 신호 API | 0 | 수집 실패 |
| 0 | UTIC | 계획 조회 |
| UTIC | 0 | 신호 계획 |
| 운영자 | 0 | 조회 요청 |
| 운영자 | 0 | 이슈 코멘트 |
| 0 | 운영자 | 관제 정보 |
| 관리자 | 0 | 조회 요청 |
| 관리자 | 0 | 정보 통제 |
| 관리자 | 0 | 계획 통제 |
| 관리자 | 0 | 현장 통제 요청 |
| 관리자 | 0 | 기준 설정 |
| 0 | 관리자 | 관제 정보 |
| 0 | 관리자 | 통제 결과 |

`계획 조회`와 `신호 계획`에는 “승인 후”라고 덧붙인다. 미승인이면 이 두 흐름은 없고, 계획은 관리자의 `계획 통제`와 픽스처 쪽 시드로 채운다. 점선으로 그리거나 각주로 적는다.

`수집 요청`은 실시간 호출을 할 때만 있다. 픽스처를 읽을 때는 API로 나가는 화살표를 그리지 않는다. 쿼터 숫자 5,000은 배경도 흐름 이름이 아니다. 수준 1의 수집 처리 안에서 다룬다.

## 5. 수준 0

배경도의 원 `0`을 아래 일곱 프로세스로 연다.

| 번호 | 이름 | 하는 일 |
|------|------|---------|
| 1.0 | 수집·정규화 | 픽스처 또는 실시간 API에서 상태를 받아 원본으로 남기고, 초·표준 점등코드로 바꾼다 |
| 2.0 | 계획 관리 | UTIC, 관리자 수정, 추정, 시드를 같은 계획으로 저장하고 ID를 매핑한다 |
| 3.0 | 오류 검지 | 정규화 상태와 계획을 규칙으로 대조해 등급과 분기를 만든다 |
| 4.0 | 제공 통제 | 정상 복사, 자동 보정, 관리자 대체·차단. 쓰는 곳은 제공 값뿐이다 |
| 5.0 | 이슈 처리 | 해결 불가 건을 이슈로 등록·갱신하고, 계획 통제·현장 요청·종료를 받는다 |
| 6.0 | 관제 조회 | 대시보드, 원본과 제공 비교, 이슈, 통계를 사람에게 돌려준다 |
| 7.0 | 기준 설정 | 계정, 수집 대상, 임계값, 감시 제외, 쿼터 한도를 저장한다 |

배치: 왼쪽이 `1.0`·`2.0`, 가운데가 `3.0`·`4.0`·`5.0`, 오른쪽이 `6.0`·`7.0`. 사람은 위, 저장소는 아래.

### 5.1 데이터 저장소

아키텍처의 저장 집합 이름을 괄호로 같이 적으면 나중에 ERD와 맞추기 쉽다.

| 번호 | 이름 | 아키텍처 | 누가 쓰나 | 주의 |
|------|------|----------|-----------|------|
| D1 | 원본 수신 | S-RAW | 1.0이 추가, 6.0이 읽기 | 다른 프로세스의 쓰기 화살표 금지 |
| D2 | 신호 계획 | S-PLN | 2.0이 읽고 쓰기, 3.0이 읽기 | 상태 원본과 다른 저장소 |
| D3 | 검증 결과 | S-VAL | 3.0이 추가, 6.0이 읽기 | |
| D4 | 제공 데이터 | S-PUB | 4.0이 읽고 쓰기, 3.0·6.0이 읽기 | 자동 보정과 차단은 여기만 |
| D5 | 이슈 | S-ISS | 5.0이 읽고 쓰기, 6.0이 읽기 | |
| D6 | 통제 이력 | S-CTL | 4.0·5.0이 추가, 6.0이 읽기 | 지우기 화살표 없음 |
| D7 | 기준 설정 | S-USR, 규칙·수집·제외 | 7.0이 읽고 쓰기, 1.0·3.0·5.0이 읽기 | |
| D8 | 통계 집계 | S-STA | 6.0이 읽기 | 집계를 만드는 처리는 6.0 안으로 둔다. 별도 원을 추가하지 않는다 |

교차로 마스터는 D1과 따로 두지 않는다. `녹화 상태`와 `상태 응답`에 맵이 들어 있고, 1.0이 D1과 함께 다룬다고 각주에 적는다.

### 5.2 프로세스 사이 흐름

| 출발 | 도착 | 데이터 |
|------|------|--------|
| 1.0 | 3.0 | 정규화 상태 |
| 2.0 | 3.0 | 해당 시각 계획 |
| 3.0 | 4.0 | 정상 상태 |
| 3.0 | 4.0 | 해결 가능 오류 |
| 3.0 | 5.0 | 해결 불가 오류 |
| 5.0 | 2.0 | 수정 계획 |
| 5.0 | 4.0 | 제공 차단 요청 |
| 5.0 | 3.0 | 재검증 요청 |

`재검증 요청`은 계획이 바뀐 뒤 3.0이 다시 읽게 하는 흐름이다. 마름모로 “재검증?”을 그리지 않는다.

읽기·쓰기는 저장소 화살표로 그린다. 위 표에 없는 것은 저장소를 통한다.

- 1.0은 수집 전에 D7의 `쿼터·수집 대상`을 읽는다.
- 3.0은 D7의 `규칙 임계값`과 D4의 `직전 제공 값`을 읽는다. 미매핑이면 계획 대조 없이 상태 품질만 판정한다. 그 사실은 `검증 결과`에 남고, UTIC로 새 화살표를 만들지 않는다.
- 5.0은 D7의 `감시 제외`를 읽어 제외 기간의 신규 이슈를 만들지 않는다.
- 4.0의 자동 보정은 D6에 `자동 보정 기록`을 추가한다. D1에는 아무것도 쓰지 않는다.
- 6.0은 D1, D3, D4, D5, D6, D8을 읽어 `관제 정보`로 내보낸다. D1과 D4를 한 이름으로 합치지 않는다. 화면의 원본/제공 비교가 이 두 읽기다.

### 5.3 배경도 흐름이 들어가는 곳

| 배경도 데이터 | 수준 0에서 닿는 프로세스 |
|---------------|--------------------------|
| 녹화 상태, 수집 요청, 상태 응답, 수집 실패 | 1.0 |
| 계획 조회, 신호 계획 | 2.0 |
| 계획 통제 | 5.0에서 받아 `수정 계획`으로 2.0에 넘긴다 |
| 정보 통제 | 4.0 |
| 현장 통제 요청, 이슈 코멘트 | 5.0 |
| 조회 요청, 관제 정보, 통제 결과 | 6.0 |
| 기준 설정 | 7.0 |

`통제 결과`는 6.0이 D6을 읽어 관리자에게 보여주는 흐름이다. 현장 요청을 외부로 다시 나가지 않게 하려고, 결과의 도착은 관리자뿐이다.

## 6. 수준 1

부모 프로세스 하나당 한 장이다. 장의 제목에 부모 번호를 쓴다. 예: `1.0 수집·정규화 상세`.

균형 규칙: 부모로 들어오고 나가던 흐름은 자식 중 하나가 같은 이름·같은 방향·같은 상대(외부, 다른 프로세스, 저장소)로 가져야 한다. 부모 장에 없던 외부 개체나 저장소를 자식 장에서 새로 만들지 않는다. 자식들끼리의 흐름은 새로 만들어도 된다.

### 6.1 `1.0 수집·정규화`

부모 입출력: 녹화 상태, 수집 요청, 상태 응답, 수집 실패, D7 읽기, D1 쓰기, 정규화 상태.

| 번호 | 이름 | 입력 | 출력 |
|------|------|------|------|
| 1.1 | 쿼터 확인 | D7 `쿼터·수집 대상` | 수집 허가, 쿼터 중단 |
| 1.2 | 상태 수신 | 녹화 상태, 또는 수집 허가 뒤의 상태 응답·수집 실패 | 수신 원본 |
| 1.3 | 원본 적재 | 수신 원본 | D1 `원본 수신` |
| 1.4 | 단위·코드 정규화 | D1에서 읽은 원본 | 정규화 상태. 코드 매핑 실패도 이 흐름에 실어 3.0으로 보낸다 |

1.1에서 쿼터 중단이면 1.2는 실시간 API로 `수집 요청`을 보내지 않는다. 픽스처의 `녹화 상태`는 1.1을 거치지 않고 1.2로 들어가게 그린다. 픽스처는 호출 횟수에 넣지 않는다.

1.3이 D1에 쓴 뒤에만 1.4가 읽는다. 순서를 바꾸면 원본보다 정규화가 먼저가 된다.

### 6.2 `3.0 오류 검지`

부모 입출력: 정규화 상태, 해당 시각 계획, 재검증 요청, D4 읽기, D7 읽기, D2 읽기, D3 쓰기, 정상 상태, 해결 가능 오류, 해결 불가 오류.

| 번호 | 이름 | 입력 | 출력 |
|------|------|------|------|
| 3.1 | 대조 입력 구성 | 정규화 상태, 해당 시각 계획, 재검증 요청, D4 `직전 제공 값`, D7 `규칙 임계값` | 대조 묶음 |
| 3.2 | 규칙 판정 | 대조 묶음 | 규칙별 판정 |
| 3.3 | 등급 분류 | 규칙별 판정 | D3 `검증 결과`, 그리고 정상 상태 / 해결 가능 오류 / 해결 불가 오류 중 하나 |

3.3에서 나가는 세 흐름의 합이 부모 3.0에서 나가던 세 흐름과 같다. 미매핑은 3.1에서 계획을 빼는 것이지, 새 외부 시스템으로 가는 화살표가 아니다.

### 6.3 `4.0 제공 통제`

부모 입출력: 정상 상태, 해결 가능 오류, 정보 통제, 제공 차단 요청, D4 읽기·쓰기, D6 쓰기.

| 번호 | 이름 | 입력 | 출력 |
|------|------|------|------|
| 4.1 | 제공 값 반영 | 정상 상태 | D4 `제공 데이터` |
| 4.2 | 자동 보정 | 해결 가능 오류, D4 | D4 `보정된 제공 값`, D6 `자동 보정 기록` |
| 4.3 | 수동 대체·차단 | 정보 통제, 제공 차단 요청, D4 | D4 `제공 데이터`, D6 `수동 통제 기록` |

4.2와 4.3의 쓰기 화살표는 D4와 D6뿐이다. D1로 선을 긋지 않는다.

### 6.4 `5.0 이슈 처리`

부모 입출력: 해결 불가 오류, 이슈 코멘트, 계획 통제, 현장 통제 요청, D5 읽기·쓰기, D6 쓰기, D7 읽기, 수정 계획, 제공 차단 요청, 재검증 요청.

| 번호 | 이름 | 입력 | 출력 |
|------|------|------|------|
| 5.1 | 이슈 등록·갱신 | 해결 불가 오류, D5, D7 `감시 제외` | D5 `이슈`. 같은 교차로·규칙의 미종료 이슈가 있으면 새로 만들지 않고 갱신 |
| 5.2 | 이슈 조치 접수 | 이슈 코멘트, 계획 통제, 현장 통제 요청 | 코멘트, 수정 계획, 현장 요청 기록, 제공 차단 요청 |
| 5.3 | 조치 반영 | 수정 계획, 현장 요청 기록, 제공 차단 요청 | `수정 계획`은 2.0으로, `제공 차단 요청`은 4.0으로, 현장 요청은 D6에만 추가 |
| 5.4 | 재검증 요청 | D5에서 읽은 종료 전 이슈 | 3.0으로 `재검증 요청` |

5.3에서 시스템 밖으로 나가는 선은 없다. 현장 통제 요청의 도착은 D6이다.

## 7. 그리기 전에 지울 것

아래에 해당하면 그 화살표는 잘못된 것이다.

| 그리기 쉬운 선 | 왜 지우나 |
|----------------|-----------|
| 제공 통제 → 원본 수신 | 자동 보정과 관리자 수정은 제공 값만 바꾼다 |
| 이슈 처리 → 현장 신호제어기 | 요청은 기록만 한다. 실전송이 없다 |
| 운영자 → 제공 통제, 운영자 → 계획 관리 | 통제와 계획 수정은 관리자만 |
| 운영자 또는 관리자 → 실시간 신호 API | API 호출은 1.0만 한다. 브라우저는 외부로 나가지 않는다 |
| 원본 수신 → 제공 데이터 | 저장소끼리는 직접 잇지 않는다. 사이에 프로세스가 있어야 한다 |
| 정상/오류를 한 화살표 “결과”로 합치기 | 4.0과 5.0으로 가는 데이터가 다르다 |
| 쿼터 초과를 마름모로 표현 | 1.1의 `쿼터 중단` 흐름으로 그린다 |
| 통계 화면, 로그인 화면 상자 | 화면 이름은 프로세스가 아니다. 나가는 데이터는 `관제 정보`다 |

## 8. 다 그린 뒤 검사

장을 바꿔 가며 아래를 확인한다.

1. 배경도의 화살표마다 수준 0에 같은 이름의 화살표가 있고, 도착 프로세스가 5.3절 표와 같다.
2. D1로 들어가는 화살표는 1.3뿐이다.
3. 현장 신호제어기로 향하는 화살표가 한 개도 없다.
4. 운영자에서 출발하는 흐름은 `조회 요청`과 `이슈 코멘트`뿐이다.
5. 모든 화살표에 명사 이름이 있다.
6. 모든 프로세스에 들어오는 흐름과 나가는 흐름이 각각 하나 이상 있다.
7. 수준 1 네 장의 바깥 흐름을 합치면 그 부모의 수준 0 흐름과 이름이 같다.
8. UTIC 흐름에는 승인 후라는 표시가 있다. 미승인일 때의 계획은 관리자와 시드 쪽에 남아 있다.

번호를 먼저 적고 선을 나중에 긋는다. 선을 먼저 치면 원본과 제공 값이 한 저장소로 붙기 쉽다.
